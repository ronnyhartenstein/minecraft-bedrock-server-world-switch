# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `docker compose up -d --build` – build and run the switcher UI (only way to run it; there is no local `npm start` workflow since the app talks to `/var/run/docker.sock` and expects to run containerized)
- `docker compose logs -f` – tail the UI's logs
- `cd app && npm install` – install dependencies (dockerode, express) if editing outside the container
- No test suite and no lint script exist (`app/package.json` only defines `start`).

## Architecture

This is a small Node/Express app (`app/`) that lets a user switch between multiple Minecraft Bedrock worlds, each running in its own Docker container, without ever having two running at once (they share host UDP port 19132).

**Docker-outside-of-Docker**: the UI itself runs in a container (`realm-switcher-ui`, see `docker-compose.yml`) with `/var/run/docker.sock` bind-mounted in, and uses `dockerode` (`app/src/docker.js`) to talk to the *host's* Docker daemon. This means any bind-mount source paths the app passes to `createContainer` (e.g. for `-v <data>:/data`) must be **host** paths, not paths inside the UI container. That's why `HOST_DATA_PATH` (env var, set by the user in `.env`) is passed straight through as the bind source, separately from `/worlds` (a read-only mount used only so the UI can list world folder names).

**Container naming convention matters**: world containers are named `mc-realm-<slug>` (`CONTAINER_PREFIX` in `app/src/config.js`), and `app/src/docker.js` finds/manages them by matching that name prefix. The UI's own container is deliberately named `realm-switcher-ui` (*not* `mc-realm-*`) so it can't match its own filter and try to stop itself — `docker.js` additionally guards against this via `OWN_HOSTNAME` (Docker sets a container's hostname to its own container ID). Keep both safeguards if renaming anything here.

**Data flow / module responsibilities**:
- `app/src/config.js` — static defaults: the `DEFAULT_ENV` block mirrors the original single-container `docker run` command (OPS, DIFFICULTY, GAMEMODE, etc.), plus paths/constants read from env vars (`HOST_DATA_PATH`, `WORLDS_MOUNT`, `CONFIG_FILE`, `PORT`).
- `app/src/worlds.js` — discovers world folders under `/worlds` and reconciles them against the persisted `app/data/worlds.json` (`syncWorlds()`): new folders get auto-added with defaults, folders that disappear are flagged `missing: true` rather than deleted (no data loss). Per-world `env` overrides in `worlds.json` are merged on top of `DEFAULT_ENV` at container-creation time.
- `app/src/docker.js` — all Docker Engine API calls via `dockerode`. `switchToWorld()` is the core operation: stop any other running `mc-realm-*` container, `ensureContainerForWorld()` (create if it doesn't exist yet, using the merged env + `HOST_DATA_PATH` bind + fixed UDP port binding + `RestartPolicy: unless-stopped`), then start it. `stopWorld()` just stops a world's own container without starting anything else (used by the "Stoppen" button so the server can be turned off entirely); the `unless-stopped` restart policy respects an explicit stop across a Docker/Windows restart. `streamLogs()` returns a live `container.logs({follow:true})` stream for the log-viewer feature (see below); it's backed by `waitForContainer()`, a short bounded poll (10×500ms) for the container to exist, needed because the frontend opens the log stream immediately after `POST /activate` while `switchToWorld()` may still be stopping the previous container.
- `server.js` — Express app exposing `GET /api/worlds`, `GET /api/status`, `POST /api/worlds/:id/activate`, `POST /api/worlds/:id/stop`, `GET /api/worlds/:id/logs`. The three mutating/streaming routes fire the Docker operation asynchronously; `/activate` and `/stop` respond `202` immediately while module-level `switching`/`stopping` variables track the in-flight target so `GET /api/worlds` can report a `starting`/`stopping` status before the container reflects it. `/logs` is a Server-Sent Events endpoint: it reads the dockerode log stream, buffers to newline boundaries via `StringDecoder` (containers run with `Tty: true`, so this is a plain-text byte stream, no stdout/stderr demuxing needed), and writes one `data:` frame per log line. Cleanup is critical here — `req.on("close", cleanup)` destroys the dockerode stream on any disconnect (client-closed, tab-closed, or network drop), and a 20s `: ping` comment line is a cheap defensive heartbeat. A container that isn't running yet (or has stopped) makes the log stream end immediately with an `event: ended` SSE frame; the browser's native `EventSource` auto-reconnects on that (desired — it's how a stream "waits" for a not-yet-started container), but gives up permanently on a hard `404` (world has no container at all), which is also desired. Serves `app/public/` statically.
- `app/public/` — plain HTML/CSS/JS frontend (no build step, no framework): tile grid, confirm-before-switch dialog, polls `/api/worlds` every 2s to reflect status changes. A "Logs" button appears on any tile with an existing container (`running`/`starting`/`stopping`/`stopped`) and opens a second overlay (`#logs-overlay`, separate from the confirm dialog's `#confirm-overlay`) that streams into a `<pre>` via `EventSource`; `confirmSwitch()` auto-opens this log overlay right after triggering `/activate` so starting a world immediately shows its boot progress.

**Known constraint from testing**: switching away from a world can take up to the `docker stop` grace timeout (30s, hardcoded in `stopContainer()` in `docker.js`) if the running server doesn't exit promptly on SIGTERM — this is expected with the real itzg/minecraft-bedrock-server image (it saves the world on SIGTERM) and the frontend's poll loop has a 90s timeout before it shows an error.
